## 0. 心智模型：交易所 = 自动撮合的菜市场

想象一个特殊菜市场，卖的是「股票 / 期货合约」。它和普通菜市场有三点不同：

1. **买卖双方不见面**，全部把意向报给市场中央的「撮合机器」。
2. **价格不是喊出来的，是排队排出来的**——所有报价按价格高低排成两列队伍。
3. **成交由机器自动完成**——一旦买方出价 ≥ 卖方要价，立即撮合。

这个「排队 + 自动撮合」的核心结构叫**订单簿（Order Book）**。理解它，后面全部概念都顺了。

---

## 1. 订单簿与价差

某只股票此刻的订单簿：

```
          卖方队伍（想卖的人，按价从低到高）
   卖三    10.3 元   ← 挂着 500 股要卖
   卖二    10.2 元   ← 挂着 800 股要卖
   卖一    10.1 元   ← 挂着 300 股要卖   ← 最低要价
   ─────────────────────────────────── ← 买卖之间的空隙 = 价差 spread
   买一    10.0 元   ← 挂着 600 股想买   ← 最高出价
   买二     9.9 元   ← 挂着 400 股想买
   买三     9.8 元   ← 挂着 700 股想买
          买方队伍（想买的人，按价从高到低）
```

- **卖一~卖五**（ask，委卖）：卖方最便宜的 5 档报价。
- **买一~买五**（bid，委买）：买方最贵的 5 档报价。
- **价差（spread）**：买一与卖一之间的缝隙。买一 10.0 和卖一 10.1 之间没有成交，因为买方出价还没够到卖方要价。要成交，必须有人「跨过缝隙」。

> **代码落点**：`TickData` 里的 `bid_price_1..5` / `ask_price_1..5` 及对应 `bid_volume_*` / `ask_volume_*`，正是这张订单簿前 5 档的实时快照（见 `vnpy/trader/object.py` 的 `TickData`）。这 20 个字段不是凑数，而是**市场深度**的真实写照。

## 2. 一笔交易怎么发生：OrderType（订单类型）

你想买这只股票，有两种基本下单方式。

### 方式 A：限价单（Limit Order）——「我只肯出这个价，买不到就排队等」

- 你说「买 300 股，每股最多 10.0 元」。当前最低卖价 10.1，你够不到 → **不立即成交**，你的单子加入买方队伍排在「买一 10.0」等待。
- 若出价 10.1（等于卖一）→ 机器立刻撮合成交。
- **优点**：价格可控，绝不买贵。**缺点**：可能一直不成交。
- 代码：`OrderType.LIMIT`（量化最常用，因为价格可控）。

### 方式 B：市价单（Market Order）——「不管价格，现在就要成交」

- 机器直接从卖一开始吃单。买得多时会把卖一、卖二……越吃越高，导致**滑点（slippage）**——实际成交均价比你看到的价格差。
- **优点**：几乎一定成交。**缺点**：价格不可控。
- 代码：`OrderType.MARKET`。

### 其余类型 = 限价单 + 附加规则

| 代码 `OrderType` | 中文 | 金融含义 |
|---|---|---|
| `LIMIT` | 限价 | 指定价格，够不到就排队等（最常用） |
| `MARKET` | 市价 | 不指定价格，立即成交，有滑点风险 |
| `STOP` | 停止单 | 价格突破 X 才触发下单（止损/追涨用） |
| `FAK` | Fill and Kill | 立即成交能成的部分，**剩余立刻撤销**（不排队） |
| `FOK` | Fill or Kill | **要么全部立即成交，要么全部撤销** |
| `RFQ` | 询价 | 冷门品种没人挂单时，主动喊「谁来报个价」 |

> **主线**：OrderType 回答「我这笔单子想以什么方式进入市场撮合」。

## 3. 下单之后经历什么：Status（委托状态机）

你的单子进了市场，它的「命运」会经历一系列状态。这就是 `Status`——一台描述委托从生到死的**状态机**。

以「买 1000 股 @ 10.1 限价」为例：

```
① SUBMITTING（提交中）
   指令飞向交易所途中，交易所还没确认。
        │ 交易所确认：合法，已挂进订单簿
        ▼
② NOTTRADED（未成交 / 已挂单）
   在订单簿里排队，还没有任何一股成交。
        │ 有人卖过来，先成交 300 股（剩 700 排队）
        ▼
③ PARTTRADED（部分成交）
   成交了一部分，还剩一部分挂在市场。
        │ 剩下 700 股也成交
        ▼
④ ALLTRADED（全部成交）  ← 正常终点
   1000 股全成，委托完成使命，从订单簿消失。
```

两个**非正常终点**：

- **CANCELLED（已撤销）**：还没成交完，主动撤回未成交部分。
- **REJECTED（拒单）**：交易所直接拒绝，没进订单簿。常见原因：价格没对齐最小变动价位、钱不够、非交易时段、超涨跌停。

**为什么代码里要有 `is_active()`？**

`OrderData.is_active()` 在状态属于 `{SUBMITTING, NOTTRADED, PARTTRADED}` 时返回 `True`（见 `object.py` 顶部的 `ACTIVE_STATUSES`）。金融含义：**这张委托还"活着"，还在市场里、还可能继续成交、因此还能撤销**。而 `ALLTRADED / CANCELLED / REJECTED` 是三个死亡终态。程序据此维护「当前哪些单子还挂在市场上」（OMS 的活动委托表）。

> **主线**：Status 回答「我这张委托现在走到人生哪一步了」。

## 4. 六个核心名词：委托/成交/持仓/账户/合约/行情

它们其实是**同一件事的不同侧面**，用一次买入串起来理解：

| 名词 | 代码类 | 一句话 | 生活类比 |
|---|---|---|---|
| **委托 Order** | `OrderRequest` → `OrderData` | 你的下单意向 + 状态跟踪 | 你点的那道菜（订单） |
| **成交 Trade** | `TradeData` | 真实配对的一次交割（不可撤销） | 真端上桌的那盘菜 |
| **持仓 Position** | `PositionData` | 成交累积后你现在攥着多少 | 已吃进肚子的所有菜 |
| **账户 Account** | `AccountData` | 你的钱包（可用 = 总 − 冻结） | 钱包余额 |
| **合约 Contract** | `ContractData` | 标的物的规格说明书（静态） | 菜的份量/起订规格 |
| **行情 Market Data** | `TickData` / `BarData` | 市场实时/汇总的价格信息（输入） | 市场当前的报价牌 |

几个关键点：

- **委托 ↔ 成交是一对多**：一张委托（Order）可分多笔成交（Trade）成交（大单被分批撮合）。
- **成交可累积成持仓，但成交不可撤，委托可撤**。
- **期货特殊性**：同一合约可**同时持有多头和空头**两条腿，所以 `PositionData` 带 `direction` 区分；股票只能持有正股。
- **合约为什么关键**：`pricetick`（最小变动价位）决定下单价必须对齐；`size`（合约乘数）决定期货 1 手 = 多少份标的，盈亏 = 价差 × 手数 × size，漏乘会离谱错。

### 委托的两个正交维度（理解这个 = 理解下单）

| | `Offset.OPEN`（开仓/建仓） | `Offset.CLOSE`（平仓/了结） |
|---|---|---|
| `Direction.LONG`（买入） | 买入开仓 = **做多** | 买入平仓 = 平空头 → `cover` |
| `Direction.SHORT`（卖出） | 卖出开仓 = **做空** | 卖出平仓 = 平多头 → `sell` |

- **Direction**：这笔单子是买还是卖。
- **Offset**：它是在建仓还是了结仓位。
- 这 4 格正好对应 CTA 策略的 4 个下单函数：`buy`(多开) / `sell`(多平) / `short`(空开) / `cover`(空平)。
- **市场差异**：期货有完整开/平，甚至细分平今（`CLOSETODAY`）/平昨（`CLOSEYESTERDAY`）；A 股通常只有买/卖（`Offset` 常填 `NONE`），且 T+1、不能裸卖空。

## 5. Gateway 是什么

**Gateway（网关/接口）= 你的程序和某一家券商/交易所之间的「翻译官 + 快递员」。**

**为什么需要它**：全世界券商、交易所的通信协议各不相同（CTP、XTP、IB API……），数据格式、函数名、登录方式都不一样。若策略直接对接每一家，换券商就得重写策略——灾难。

**VeighNa 的解法**：定义统一抽象接口 `BaseGateway`（`vnpy/trader/gateway.py`），规定任何接口都必须实现这几个标准动作：

- **对外发指令**（程序 → 券商）：`connect`（连接登录）、`subscribe`（订阅行情）、`send_order`（下单）、`cancel_order`（撤单）、`query_account`（查资金）、`query_position`（查持仓）、`query_history`（查历史 K 线）。
- **收回报**（券商 → 程序）：`on_tick`（新行情）、`on_order`（委托状态变了）、`on_trade`（有成交）、`on_position`（持仓变了）、`on_account`（资金变了）、`on_contract`（合约信息）。

每接入一家券商写一个具体子类（如 `vnpy_ctp`），负责把「券商私有格式」翻译成「vnpy 标准对象」。

> **一句话**：Gateway 把「五花八门的券商协议」翻译成「vnpy 统一的数据对象和标准动作」。策略只跟标准接口打交道，换券商只换 Gateway，策略一行不改。它既是行情的**生产者**（不断推 `TickData`），也是指令的**执行者**（发 `OrderRequest`）。
>
> **回测里没有真实券商**，是 `BacktestingEngine` 用历史数据模拟了 Gateway 的角色——"假装"推行情、"假装"帮你撮合。这就是阶段 4「回测撮合 vs 实盘委托」差异的根源。

## 6. Tick 与 Bar 背后的完整交易流程

### 6.1 Tick（逐笔/切片行情）——「市场的每一次心跳」

**Tick 是市场状态变化时，交易所推送的一张实时快照。** 每当订单簿变动（有新成交、挂/撤单导致盘口变化），交易所生成一个 Tick 推给你，内含：

- `last_price`（最新成交价）、`volume`（今日累计成交量）
- `bid_price_1..5` / `ask_price_1..5` + 各档挂单量（当前订单簿前 5 档）
- `limit_up` / `limit_down`（今日涨/跌停价）

**频率**：中国股票/期货通常**每 0.5 秒一张快照**（故称"切片行情"）；海外和加密货币可能**逐笔**推送。Tick 是最细粒度行情。

### 6.2 Bar（K 线）——「把一段时间的 tick 打包成一根蜡烛」

Tick 太细太多（一天几万个），大多数策略不需要这么细。把**一段时间内所有 tick 汇总成一根 K 线（Bar）**，如「1 分钟 K 线」= 这 1 分钟的 OHLCV：

- **O**pen（开）：这段时间第一笔成交价
- **H**igh（高）：最高成交价
- **L**ow（低）：最低成交价
- **C**lose（收）：最后一笔成交价
- **V**olume（量）：总成交量

对应 `BarData`（`open/high/low/close_price` + `volume`）。

### 6.3 Tick 级 vs Bar 级策略

**本质一样，只是决策的"节拍"变粗**：

- **Tick 级**：每来一个 tick（每 0.5 秒）跑一次 `on_tick()`——高频、抢盘口。
- **Bar 级**：攒够一整分钟/小时/天，才跑一次 `on_bar()`——趋势跟踪、多数中低频策略（阶段 2 的双均线就是 Bar 级）。

**关键工程细节**：真实市场只推 tick，不直接推 bar。vnpy 用 `BarGenerator` 在程序里把 tick 实时"攒"成 bar——每来一个 tick 更新当前这根 bar 的高/低/最新价，一旦跨过整分钟就把这根 bar 封口、回调 `on_bar()`。触发后，下单→成交→持仓的流程和 Tick 那一圈完全一样。

## 7. 全景总结图 + 一句话记忆表

```
        真实市场（交易所订单簿：买卖双方排队撮合）
                    │ 价格变动 → 推送
                    ▼
                【行情 = Tick】每次心跳一张订单簿快照
                    │  BarGenerator 攒一段时间
                    ▼
                【行情 = Bar】一根 K 线 OHLCV
                    │
          ┌─────────┴──────────┐
          │  Gateway（翻译官）   │ ← 连券商，收行情/发指令
          └─────────┬──────────┘
                    ▼
              你的【策略】做决策
                    │ 买/卖(Direction) + 开/平(Offset) + 方式(OrderType)
                    ▼
          【委托 Order】← 状态机 Status：SUBMITTING→NOTTRADED→PARTTRADED→ALLTRADED
                    │ 一张委托可产生多笔
                    ▼
          【成交 Trade】← 真实配对，不可撤销
                    │ 累积
                    ▼
          【持仓 Position】你攥着多少 + 均价 + 浮盈亏
          【账户 Account】钱包还剩多少（可用 = 总 − 冻结）
                    │
          全程参照【合约 Contract】规格：pricetick(价格精度)、size(乘数)
```

| 概念 | 一句话 | 类比 |
|---|---|---|
| 行情 Tick/Bar | 市场喂给你的实时/汇总价格 | 报价牌 |
| Gateway | 连券商的翻译官+快递员 | 跨国代购代理 |
| 委托 Order | 下单指令 + 状态跟踪 | 你点的菜 |
| Status | 委托走到人生哪一步 | 已下单/在做/上齐/取消 |
| OrderType | 这笔单子怎么进市场撮合 | 按菜单价点 vs 多少钱都行马上要 |
| 成交 Trade | 真实配对的一次交割 | 真端上桌的菜 |
| 持仓 Position | 累积后现在持有多少 | 已吃进肚子的菜 |
| 账户 Account | 你的钱包 | 钱包余额 |
| 合约 Contract | 标的物规格说明书 | 菜的份量/起订规格 |

## 8. 补充机制：做多做空、涨跌停、T+1、保证金

这些是前面没细讲、但读代码/写策略常遇到的机制：

- **做多（Long）**：低买高卖赚差价，看涨。股票和期货都能做多。
- **做空（Short）**：先高价卖出（借来的/合约允许的），跌了再低价买回，看跌赚钱。**A 股普通账户不能裸卖空**（只能融券，门槛高），**期货天然可双向**。这就是为什么股票策略里 `sell` 前必须先有持仓。
- **涨跌停（limit up/down）**：A 股每天价格波动有上下限（通常 ±10%，ST 股 ±5%，科创/创业板 ±20%）。到了涨停价买不进（没人卖）、跌停价卖不出（没人买）。代码里 `TickData.limit_up/limit_down` 就是这两个价；回测撮合会用它判断能否成交。
- **T+1**：A 股**今天买入的股票，当天不能卖**，要等下一交易日。期货是 T+0（当天可平）。这就是 `PositionData.yd_volume`（昨仓）存在的意义——区分「可平的昨仓」和「当天不可卖的今仓」。
- **保证金 / 杠杆（期货）**：期货买 1 手不用付全款，只付一部分「保证金」（如 10%），相当于 10 倍杠杆——放大盈亏。`AccountData.frozen` 里就含被占用的保证金。股票现货无杠杆（除非融资）。
- **手续费 / 滑点**：每笔成交要付手续费（`rate`，按成交额比例），实际成交价常比预期差（`slippage`）。回测里必须设置真实的 `rate/slippage/size/pricetick`，否则回测结果虚高、严重失真。
